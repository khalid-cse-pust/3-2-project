# Database Schema and Relationships

This document outlines the data architecture of the **Student Hall Management System**, including entity definitions and the relationships between them. The system uses **MongoDB** as a NoSQL database with **Mongoose** for schema modeling.

## 1. Entity Definitions

### A. User Entity
The core entity representing all individuals in the system.
- **Fields:**
  - `_id`: Unique Identifier (Generated by MongoDB).
  - `name`: Full Name.
  - `email`: Unique email for login.
  - `studentId`: Unique University ID (Optional for non-student roles).
  - `role`: Role identifier (`student`, `admin`, `staff`).
  - `password`: Hashed security credential.
  - `isResidential`: Boolean flag indicating hall residency.

### B. Application Entity
Represents a student's request for hall residency.
- **Fields:**
  - `user`: Reference (Foreign Key) to the User.
  - `studentId`: Redundant ID for quick lookup.
  - `document`: URL/Path to the verification file.
  - `status`: Lifecycle state (`pending`, `approved`, `rejected`).
  - `remarks`: Feedback from the Admin.

### C. Problem Entity
Represents a maintenance or facility issue reported by a resident.
- **Fields:**
  - `user`: Reference (Foreign Key) to the reporter.
  - `category`: Type of issue (Plumbing, Wi-Fi, Electrical, etc.).
  - `description`: Detailed text of the problem.
  - `image`: URL/Path to the evidence photo.
  - `status`: Resolution state (`pending`, `assigned`, `in-progress`, `resolved`).

## 3. Relationship Logic

### 1. User to Application (One-to-One / One-to-Zero)
- **Type:** 1:1 (Logical)
- **Description:** A specific **User** (student) can submit only **one** residency application. While the database allows multiple entries, the business logic restricts students to a single active application.
- **Connection:** The `Application` schema stores the `user._id` as a reference.

### 2. User to Problem (One-to-Many)
- **Type:** 1:N
- **Description:** A single **User** (student) can report **multiple** different problems over time (e.g., a broken light today and a plumbing leak next week).
- **Connection:** Each `Problem` entry contains the `user._id` of the student who reported it.

---

## 4. Data Constraints
- **Referential Integrity:** If a User is deleted, the system logic should ideally handle the "orphaned" Applications and Problems (Cascade or Restrict).
- **Uniqueness:** The `email` and `studentId` are unique across the `User` collection to prevent duplicate accounts.
- **Enum Validation:** Status fields use strict Enums (e.g., an application status cannot be "completed", it must be "approved" or "rejected").
